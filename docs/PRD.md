## 1. 项目概述

### 1.1 背景
集团已有成体系的职位规则（`testingdata/原始文件/Position.md`）与阶段化组织树数据（`testingdata/原始文件/Org-Chart3.md`，历史版 `Org-Chart.md` / `Org-Chart2.md` 仅存档）。数据流为：

```
原始 Org-Chart3.md（唯一支持格式）
    ↓  数据清洗（系统内置模块）
Position.csv 模版文件（编号列填临时 T 占位；迭代导入带正式 ID）
    ↓  用户下载、编辑、确认（人工 review）
上传至系统导入（系统分配 P/PA 编号）
    ↓  数据入库
岗位全生命周期管理 + 人员管理 + 组织架构图
```

系统覆盖三大核心能力：
1. **岗位（Position Number）全生命周期管理**：建档 → 开启 → 招聘 → 在职 → 空缺 → 关闭/冻结，全程可追溯。
2. **人员信息管理**：员工档案，并挂编到具体岗位。
3. **组织架构图 / 汇报线**：以岗位为节点生成**汇报线树**，正确展示直线（Solid-line）与虚线（Dotted-line）汇报关系。

### 1.2 目标
- Web 界面操作，**PostgreSQL** 作为持久化存储，一条命令启动。
- 数据来源为 Org-Chart 原始文件，通过清洗模块转换为标准 CSV 后导入系统。
- 岗位状态变化全程可追溯（生命周期事件时间线）。
- 组织架构图以岗位汇报关系为准，真实反映报告线。
- 外部 API 采用 JWT 认证，确保访问安全。
- 支持并发编辑，冲突时采用合理的版本控制策略。
- 开发/测试/生产三环境数据库物理隔离，同机不同库 `hr_db_{env}`，开发操作不可影响生产（见 §7D）。

### 1.3 非目标（V1 明确不做）
- 多租户、复杂权限；复杂审批流；薪资、考勤、绩效、招聘全流程、社保。
- 移动端深度适配（桌面浏览器优先）。

> 注：源文件中的 📋 外包岗已纳入（V2.1 起），需导入系统，职位类型 `External Employee`（见 §3.7 / §4 F5.2）。

## 2. 术语定义

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 职位 | Position | 组织最小颗粒，描述「干什么活」（职能本身），**不含工作范围**。一个职位可对应 1+ 个岗位编号。 |
| 岗位编号 | Position Number | 具体编制名额（slot），编号由系统强制分配：正式岗 `P{seq}`、外包岗 `PA{seq}`（§3.1），是生命周期管理与占用员工的主体。 |
| 工作范围 | Scope | Family / Global / Regional / Country·国家 四类，独立字段维护；v2.3 起与岗位编号解耦（不编入编号）。 |
| 隶属公司 | Company | 岗位所属法人实体（Legal Entity），如 `Peeters Capital Holding SPRL`、`Soparfi S.à r.l.`。 |
| 级别 | Level | 个人贡献者 B6~B10b / 管理岗 M7~M12b（见 §3.6）。 |
| 直线经理 | Solid-line Manager | 该岗位的直接汇报岗位；唯一。构成组织树主干。源文件按职位名书写，导入时系统解析为岗位引用。 |
| 虚线经理 | Dotted-line Manager | 矩阵式职能汇报岗位（0~N 个）。源文件按职位名书写，导入时系统解析为岗位引用。 |
| 法律强制/可选 | Legal Mandatory / Optional | 法律强制·内部全职不可外包 / 法律强制·允许第三方外包 / 可选（集团内控推荐）/ 纯后勤可选，四类。 |
| 职位开启日/关闭日 | Opening / Closing Date | 岗位生命周期的起止日期（数据源为年份精度）；`N/A` = 无关闭日（仍在生效）。 |
| 生命周期事件 | Position Event | 岗位每次状态变更的记录（原→新状态、时间、备注、关联员工）。 |
| 家族自然人 | Family Natural Person | 集团顶层股东（创始人/家族），非系统内岗位；P063/P066 等直报对象。 |

## 3. 岗位数据规则（源自 Position.md，系统需遵循）

### 3.1 岗位编号规则（v2.3 重制：系统强制分配）

> **⚠️ v2.3 决策（2026-08-23，覆盖以下历史规则）**：源文件（Org-Chart / CSV）中的岗位编号**一律忽视**，编号由系统在导入/创建时**正式分配**：
> - **正式岗**（Employee / Consultant）→ `P{seq}`：P1、P2、…（纯序号，无范围后缀）
> - **外包岗**（External Employee）→ `PA{seq}`：PA1、PA2、…（独立序列）
> - 序号取库内同系列当前最大值 +1，全局持久；三库清理后自然从 1 起。
> - **导入幂等键 = 职位名 + 隶属公司 + 国家或地区 + 开启日**（4 列）；直线/虚线经理引用按**职位名**解析。
> - **编号与工作范围解耦**：范围/国家信息存独立字段，不编入编号。
> - **临时占位（T 序号）**：清洗/导出阶段编号仅为临时占位 `T{seq}`，供 review 识别岗位/经理，不占正式编号池、不跨轮累积、无回归；导入落库后重写为正式编号。
> - **命名不承载编制序号**：同名多编制靠幂等键（+开启日/备注/直线经理）区分，不靠改岗位名（§3.7/F4）。
> - **两段式识别**：首次导入=播种（不校验内容），迭代导入=基于导出全量 upsert（带 ID 认老、幂等键认新，见 F4）。

- 历史格式（仅存量参考，已废弃）：`P{职位序号}-{工作范围编号}`；Country 级：`P{职位序号}-4-{国家编号}`。

> ⚠️ 历史说明（v2.3 起不再适用，仅记录）：旧数据中 `Real Estate Compliance Manager`（P024~P027）、`Statutory MLRO Manager`（P013/P028/P054）、`Receptionist`（P045/P088）等**同一职位名使用不同 P 序号**，与旧「共享 P 序号」规则不符。v2.3 编号重制后该问题消解：所有编号由系统按 P/PA 纯序号序列全新分配。

### 3.4 汇报关系（岗位级）
- **直线经理**：直接汇报岗位（组织树上一级），存储为岗位外键，唯一。源文件按职位名书写，导入时系统解析。
- **虚线经理**：矩阵式职能汇报。典型：各法人 MLRO 对集团 Global AML Compliance Officer、各投资岗对 Global Investment Governance Manager、各区内审联络员对 Global Internal Audit Manager、各区域 IT 岗对 Global System Support Specialist、各属地合规外包岗对 Global Contract Governance Manager。
- 后端校验直线关系**无环路**、虚线无重复。

| 文件 | 角色 |

| `Org-Chart3.md` | **当前唯一支持的源文件格式**（阶段化组织树：根节点→公司→类型标记→岗位行 `英文名 - 中文名 【法律分类】(Opening: YYYY)` + 权责说明续行；无 P 编号） |

### F0 主数据配置管理（页面置于最顶部）

统一维护系统各类字典主数据，供岗位/员工表单下拉与筛选使用。

| 主数据项 | 说明 | 初始化 |

| **外部合作公司** External Company（v2.4） | 独立主数据：不在系统内设岗、仅作为股权等关系引用的外部法人实体；新增/编辑/删除；**启停由关闭日期管理**（v2.4.1，弃用启用开关）；被股东行引用时禁止删除；**不出现在岗位「隶属公司」下拉** | 空（用户按需维护） |

| **国家/地区** Country | 新增/编辑；工作范围=Country 时的**二级菜单** | 按 §3.2 9 个国家初始化 |
| **法律强制/可选** Legal Category | 新增/编辑；用于岗位「法律强制/可选」下拉 | 按 §3.5 四类初始化 |
| **职位类型** Position Type | 新增/编辑；用于岗位「职位类型」下拉 | 按 §3.7 三类初始化（Consultant / Employee / External Employee） |
| **税区（税率挂载单位）** Tax Zone | 选定工作地点挂到**国家级**或**城市级**税率集（v2.3，见 F1.6） | 空（用户按税区配置） |
| **员工用工税额** Employment Tax | 按**税区**（国家/地区或城市）维护税务科目与税率（见 F1.6） | 空（用户按税区配置） |

- **下拉过滤规则**：岗位管理的**直线经理 / 虚线经理**下拉框，仅显示**管理岗**（级别以 `M` 开头，如 M7 / M8a / M10 / M12b）的岗位，个人贡献者（B 级）岗位不出现。
- 主数据被岗位引用后，删除需确认或禁止删除（改状态停用）。

#### F0.1 隶属公司扩展与股权结构（v2.4）
- **公司字段扩展**：`开业日期 opening_date` / `关闭日期 closing_date`（Date，可空；年份精度数据按 `YYYY-01-01` 存）；`closing_date` 有值 ⇔ 公司视为关闭（与 `is_active` 联动：填关闭日自动置停用，清空恢复启用）。
- **关闭前置校验（v2.4.1）**：设置公司 `closing_date` 时，名下全部岗位（`position_numbers.company_id`）必须均为 **Closed**，否则拒绝；公司关闭后不出现在岗位管理「隶属公司」下拉（不可挂新岗；编辑既有岗位保留原值）。
- **删除保护（v2.4.1）**：隶属公司支持物理删除，但被**岗位**（company_id / prev_company_id）、**股权结构**（内部股东行）、**转调目标**（employees.target_company_id）或 **HR 绑定**（user_companies）任一引用时禁止删除。
- **股权结构 shareholders（0..N 子表）**：每个股东行三来源**互斥**（CHECK 兜底，恰好其一非空）：
  1. **内部公司**——下拉选择系统内 `companies`（排除自身；沿内部股东链上溯做**环检测**，A→B→A 拒绝）；
  2. **外部合作公司**——下拉选择 `external_companies` 主数据（不在系统内设岗的外部法人实体，独立维护）；
  3. **自然人**——手工输入姓名文本（家族自然人股东场景，PRD §2 术语）。
- **持股比例 ownership_pct**（可选填，Numeric(5,2)）：合计 ≠100% 时前端黄条告警、**不拦截保存**（软校验）。
- **删除保护**：外部合作公司被股东行引用时禁止删除；隶属公司沿用既有软删 + 岗位引用保护。
- **CSV 导入链路零改动**：导入自动建档仅填公司名，新字段留空由用户在主数据页补录。

### F1 职位与岗位生命周期管理

#### F1.1 职位（职能）维护
- 职位 = 职能名称（如 `Real Estate Compliance Manager`），一个职位可关联多个岗位编号。
- 职位列表：职位名、关联岗位数、各岗位编号与范围。

#### F1.2 岗位维护（岗位编号维度）
岗位编号为管理主体，字段对齐 Position.csv 17 列（含「职位类型」）：

| 字段 | 说明 | 必填 |
| --- | --- | --- |
| 职位 | 关联职位（职能） | 是 |
| 岗位编号 | 系统自动生成（正式 `P{seq}` / 外包 `PA{seq}`，§3.1），不可手工填写 | 是 |
| 隶属公司 | 法人实体 | 是 |
| 级别 | B/M 级别（§3.6） | 是 |
| 国家或地区 | 工作范围（Family/Global/Regional/Country·国家） | 是 |
| 职位开启日 | 生效日期（年份精度；存 date，年份→`YYYY-01-01`） | 是 |

| 工作职责描述 | 1~2 句概括 | 否 |
| 直线经理 | 岗位引用（唯一；下拉仅管理岗，源文件按职位名解析） | 否 |
| 虚线经理 | 岗位引用（0~N） | 否 |
| 法律强制/可选 | §3.5 四类 | 是 |
| Org-Chart中的显示 | 组织架构图展示名 | 是 |
| **职位类型** | 职位类型（Consultant / Employee / External Employee，由 F0 主数据字典维护，岗位表单下拉选择） | **否** |

- **新建岗位时以下字段可留空**：工作职责描述、税前薪资、公司份额、用工成本、备注（后续可在编辑中补充）。
- 列表：分页，按公司/工作范围/状态筛选，按名称/编号搜索。

#### F1.3 生命周期状态机（7 态，与开启/关闭日联动）
```
Planned (编制规划) ──→ Open (招聘中) ──→ Offered (已录用) ──→ Filled (在职)
     │                    │    │                                │
     ▼                    │    └──────────────┐                 ▼
  Closed/Frozen        Closed            Open             Vacant (空缺)
                       (停止招聘)       (候选人未入职)           │
                                                           ▼
                                               Closed / Frozen / Open
```
| 状态 | 说明 |
| --- | --- |
| Planned | 建档未生效；到达开启日或人工开岗 → Open |
| Open | 生效招聘中；→ Offered（录用）/ Closed（停止招聘，写入关闭日） |
| Offered | 已录用待入职；→ Filled（入职挂编）/ Open（候选人放弃） |
| Filled | 有员工占用；→ Vacant（员工离职/转岗） |
| Vacant | 曾占用现空；→ Open（重招）/ Closed（不再招聘）/ Frozen |
| Frozen | 临时冻结；→ Planned / Open（解冻） |
| Closed | 终态（写入关闭日）；如需启用建议新建岗位并记录转岗 |

- 非法流转后端拦截（如 `Planned → Filled`）。
- **导入历史数据映射**：有关闭日 → Closed（记一条关闭事件）；无关闭日 → Open（生效未占用）。

#### F1.4 生命周期历史（可追溯）
- 每次状态变更写一条事件：`岗位、原状态、新状态、变更时间、备注、关联员工`。
- 岗位详情页时间线展示；开启/关闭日写入也作为事件记录。

#### F1.5 与员工联动
| 员工动作 | 岗位联动 |
| --- | --- |
| 入职挂编 | 岗位 → **Filled**，绑定员工 |
| 离职 / 转岗出岗 | 岗位 → **Vacant**，解绑员工，生成事件 |
| 岗位间调岗 | 旧岗 → Vacant；新岗 → Filled |

- **挂编条件**：仅岗位状态为 **Open / Vacant / Offered** 时可挂编；**Filled**（已被占用）、**Closed / Planned** 时拒绝挂编。
- **挂编联动（v2.3）**：岗位类型 ↔ 员工合同属性**强制联动**，岗位的 `position_type` 决定了可挂载的员工 `employee_type`：

  | 岗位 `position_type` | 允许的员工 `employee_type` |
  |---|---|
  | Consultant | 正式 |
  | External Employee | 外包 |
  | Employee | 正式 / 实习 / 劳务 |

  不匹配的挂载（如 `外包` 合同属性挂到 `Employee` 编制）须被拒绝；该联动应在数据层强制兜底，避免「编制归类」与「用工形式」脱节产生四不像数据。
- **调岗约束**：新岗位同样须为 Open / Vacant；旧岗随调出转 Vacant。

#### F1.5b 转调与升职（v2.3，人永不脱岗）
- **转调交接**：原 HR 把人**转出到目标公司**（人仍挂原岗、原岗保持 Filled 并**锁定**，`employees` 标记「转调中」+ `target_company_id`）；目标 HR 在**待认领池**认领 → 分配**空闲目标岗**（Open/Vacant/Planned）→ 原岗→Vacant、目标岗→Filled、记转调事件、更新 `prev_*`。目标 HR 取消/拒绝 → 退回原公司、原岗继续。**人任何时刻都有岗位**。
- **升职**：两种时节——**月末升职**（财务月末生效）/ **即时升职**（当天生效）；升职当天前 Filled 老岗，生效时 Filled 新岗，**老岗默认 → Vacant**（需要时由 HR 手动 Closed）；`prev_*` 记录来源岗/公司，**工龄跟人**（hire_date 不动）。
- **成本/工资/税收跟人走**：归属 = 人所隶属公司的税区；转调/升职跨司时按**财务月边界**归属（目标 HR 财务月末认领 → 该月成本算原公司，次月起归目标公司）。
- **读可跨司、写按实体隔离**：组织图/岗位展示可见他司员工**姓名**（只读）；对员工/成本的**修改**受行级隔离约束（见 §7B）。

#### F1.6 岗位成本字段与公司份额计算
- 岗位有三个**人工成本**字段：**税前薪资（人工）**、**公司份额（人工）**、**用工成本（人工）**。
- 两种输入模式，**互斥，只能启用一种**；未启用的字段置灰不可编辑：
  1. **自动计算模式**：公司份额 = 税前薪资 × Σ(该岗位工作地点所挂**税区**全部有效税务科目税率)；用工成本 = 税前薪资 + 公司份额。
  2. **手动输入模式**：三个字段均可手工填写。
- **工作地点结构（v2.3）**：工作地点 = **国家/地区 + 城市** 两级（如 `比利时·布鲁塞尔`、`中国·上海`）。
- **税区挂载点配置（v2.3 成本引擎）**：
  - 税率集合的挂载单位**可配置**：挂到**国家级**（该国家内统一税率）或**城市级**（同一国家下按城市分拆税率，如上海/北京社保不同）。
  - **无国家兜底**：一旦某国家选择城市级挂载，则**不存在国家兜底税率**；任何未配置税率的地区，成本**无法自动计算**（返回「未配置」，不猜测估值）。
- **员工用工税额配置**（F0 主数据）：
  - 按**税区**（国家或城市）划分，每个税区有各自特定的税务项目。
  - 用户可直接增加项目，每项含：**科目**（如 Social Security、Pension、Insurance）与**税率**（百分比）。
  - 自动计算时按该税区的全部有效科目税率求和。
  - **成本键既不是 `position_type` 也不是粗粒度「国家」，而是「税区」（可精细到城市）**。
- **双口径（v2.3）**：
  - **预算成本**（岗位表）：空岗可录、预算口径、**不随人走**、自动计算按**岗位税区**；
  - **实际成本**（员工表）：Filled 真实成本、**跟人走**、自动计算按**人的归属税区**、升职转调不丢、离职留档；
  - 岗位详情显示**预算 ∪ 实际**两层（Filled 对照、空岗只预算）；实际 = join 当前占用员工。

### F4 数据导入（Position.csv，两段式识别，v2.3）

导入采用**两段式**识别——首次 vs 迭代，规则与校验强度不同（编号/幂等机制见 §3.1）。

**首次导入（系统初始化·播种）**：
- 库里无老数据可比，**不做内容一致性校验**（无对错裁判），以用户 CSV 为准逐行落库；
- 仅保留**硬唯一约束**兜底（岗位编号唯一、幂等键唯一、员工姓名唯一），防重复写入，不猜内容对错；
- 系统据此分配首批正式编号 `P{seq}`（正式岗）/ `PA{seq}`（外包岗），并返回分配明细。

**迭代导入（全量）**：
- **强制复用上次导出的 CSV 格式**；导出文件**携带正式岗位 ID**（可选「岗位ID」列，#49 定稿）；
- **带 ID 且库内存在的行 → 按正式 ID 认老岗位、更新字段**（保留编号/事件/员工关联）；带 ID 但库内不存在 → 报错该行不导入；
- **无 ID / 未携带 ID 的行 → 回退幂等键匹配认老**；均未命中 → 靠幂等键新建；
- 幂等键命中同名/同开启日双编制 → **报错**，由用户在 review 阶段区分（不在系统内猜）。

**校验规则（两段共用）**：
- **岗位编号列一律忽视**：编号由系统在导入时强制分配，命名不承载编制序号；
- 隶属公司 / 职位必填；国家或地区须可识别；关闭日早于开启日报错；开启/关闭日按年份精度解析；
- 直线/虚线经理按**职位名**解析引用；同名多岗取首个并告警；`N/A` 视为空；
- **幂等键 = 职位名 + 隶属公司 + 国家或地区 + 开启日**（4 列）；键值重复 → 报错（返回错误明细，该行不导入）。

**字段改动的正确时机**：识别锚（职位名/公司/国家/开启日）一旦落库即作为身份，此后**不支持在导入阶段改动**；需要纠正（如国家标错）→ **导入后进系统内维护**，而非重导 CSV 覆盖身份。

**编号体系（v2.3 全文）**：
- 正式编号 `P{seq}` / 外包 `PA{seq}`，纯序号、无范围后缀，**导入入库时由系统分配**；
- 清洗/导出阶段的编号仅为**临时占位（T 序号）**，供用户在 review 中识别岗位/经理，**不占正式编号池、不跨轮累积、无回归问题**；
- 导入落库后，经理引用全部重写为**正式编号**，占位符作废。

- 导入后自动生成初始生命周期事件（关闭日有值 → Closed 并记录关闭事件）。

### F5 Org-Chart 数据清洗（上传解析 → CSV 生成）

上传 Org-Chart3.md（唯一支持格式，§3.7），按 Position.csv 模版格式自动解析、清洗，输出标准 CSV 后一键导入系统。

#### F5.1 功能流程
1. 用户上传 Org-Chart3.md 或指定服务器原始文件（规则文件 Position.md 使用固定模版）
2. 系统解析树形结构，提取所有岗位（含 🧑‍💼 内部全职 + 👨‍👩‍👧 家族志愿 + 📋 外包岗）

   - 若为**迭代导入**：基于上次导出的树形格式输出，CSV 携带**正式岗位 ID**（见 F4）；
4. 用户在前端预览清洗报告 + CSV 数据，**人工 review**（可修正岗位名/公司/经理/职责等非识别锚字段）

#### F5.4 数据质量报告
- 自动修复：去除工作范围前缀（记录修复项）
- 验证：隶属公司一致性、必填字段完整性、法律分类提取（岗位编号由系统分配，不做源编号校验）

## 7B. 安全需求（JWT 认证 + 角色权限）

### 7B.1 外部 API 认证
- 外部调用的 API 端点（如 `/api/public/*` 以及非内部工具消费的接口）必须通过 **JWT（JSON Web Token）** 认证。
- 内部管理接口（系统前端使用）同样走 JWT；JWT 含 `sub/role/exp`。
- Token 过期后需刷新；无 Token 或过期 Token 返回 `401 Unauthorized`。
- 请求头格式：`Authorization: Bearer <token>`。

### 7B.2 角色与账号（v2.3）
- **角色**：`admin`（集团 full admin）/ `hr`（子公司 HR）。
- **关闭自主注册**：仅 `admin` 可创建账号并分配可管公司；无注册审批流（注册即指派人）。默认种子 `admin/admin123` 保留（`DEFAULT_ADMIN_*` 可覆盖）。
- **可管实体**：`hr` 账号经 `user_companies` 多对多绑定可管理的**法人实体**；`admin` 自带全司。

### 7B.2a 权限拆分：数据权限 → 实体，API 权限 → 接口（v2.4.3）
- **数据权限（实体维度）**：所有账号均按 `user_companies` 实体绑定约束可管理的数据范围。
- **API 权限（接口维度）**：仅外部 API 用户持有，授权表 `user_apis`（user_id + api_key），api_key 注册表见 `app/auth.py::API_SCOPES`——当前对外 2 个：**认证**（`auth.login`，登录换取 JWT）、**获取隶属公司列表**（`public.companies`）。
- **账号类型 `user_type`**：
  - **UI 用户**：仅数据权限（内部系统使用），不持有任何 API 权限；
  - **外部 API 用户**：**数据权限 + API 权限 结合**——调接口须有对应 API 授权，返回数据按实体绑定过滤。
- **执行点**：登录门槛（API 用户须持「认证」授权，未授予 403）；`/public/companies` 挂 `require_api_scope('public.companies')` 且非 admin 按可管实体过滤。admin 角色天然全量。

### 7B.3 行级权限隔离（v2.3，读可跨司·写按实体）
- **岗位不隔离**：所有 HR 可读可见岗位（含列表/详情/组织图）；`hr` 仍可维护岗位（直线/虚线接线、状态、字段）。
- **员工/成本按实体隔离**：`hr` 只能**修改**其可管实体的员工及其成本/工资/税收；未分配实体 → 404/403。**但组织架构图/岗位展示可见他司员工姓名（只读例外）**。
- **汇报接线（直线/虚线同规则）**：由**被汇报目标岗位**的操作者维护（源岗位只读不限管）。
- 账号/可管实体分配与主数据字典/导入：`admin` 维护，`hr` 只读。

### 7B.4 安全措施
- 密码使用 bcrypt 哈希存储（`app/auth.py:29`，`PyJWT/bcrypt`）。
- API 请求速率限制（`app/limiter.py:1` + `main.py:1`，`slowapi`；全局 `120/min` / IP，登录 `10/min` / 建号 `5/min` / 公共 `60/min`，超限 `429`）。
- 输入校验：所有接口输入均经过 Pydantic 校验，防止注入。
- PostgreSQL 连接使用参数化查询（SQLAlchemy ORM 天然支持），防 SQL 注入。

## 7C. 并发控制（乐观锁）

### 7C.1 冲突场景
系统为多人可同时使用的 Web 应用，需处理：两人同时编辑同一条岗位/员工数据。

### 7C.2 策略：乐观锁（版本号控制）
- 核心数据表（`position_numbers`、`employees`）增加 `version` 字段（整数，每次更新递增）。
- **读取**时返回当前版本号。
- **更新**时必须携带客户端持有的版本号：`UPDATE ... WHERE id = ? AND version = ?`。
- 若影响行数为 0（版本已变更），返回 `409 Conflict`，提示客户端刷新数据后重试。
- 前端在保存时携带版本号；收到 409 时提示用户「数据已被他人修改，请刷新后重试」。

### 7C.3 不需要锁的场景
- 岗位状态流转（POST /positions/{id}/transitions）：状态机本身有合法转换白名单，天然幂等/可重入，无需版本校验。
- 员工入职/离职：由状态机保证一致性。

## 7D. 多环境与数据库隔离（dev / test / prod）

### 7D.1 环境与命名
- 三环境取值固定：`APP_ENV=dev|test|prod`（默认 `dev`），大小写不敏感。
- 同机不同库，库名强制 `hr_db_{env}`：`hr_db_dev` / `hr_db_test` / `hr_db_prod`，禁止自定义库名/复用同一库。
- 同一 PostgreSQL 实例内三库并存，账号可共用但生产建议独立最小权限账号。

### 7D.2 配置与文件约定（合并版，`app/db.py:1`）
- 环境变量：`APP_ENV`（环境）+ `DATABASE_URL` / `DATABASE_URL_{env}`（连接串，库名必须与 `APP_ENV` 一致）。
- **单文件 `.env` 合并版**（`app/db.py:55`，`DATABASE_URL_{dev,test,prod}` 三段 + `APP_ENV` 切换，旧的 `.env.test`/`.env.prod` 仍兼容）：
  ```ini
  APP_ENV=dev
  DATABASE_URL_dev=postgresql://postgres:postgres@localhost:5432/hr_db_dev
  DATABASE_URL_test=postgresql://postgres:postgres@localhost:5432/hr_db_test
  DATABASE_URL_prod=postgresql://postgres:${POSTGRES_PASSKEY}@localhost:5432/hr_db_prod
  # 密码等敏感信息通过 ${POSTGRES_PASSKEY} 引用 shell 变量（启动前 export）
  # 也可直接设 DATABASE_URL=... 强制覆盖（优先级更高）
  ```
  `.env` 单文件内含三环境，`DATABASE_URL_{env}` 按 `APP_ENV` 自动选择；`.env.example` 为模版（含 JWT/limiter 示例）。
- 加载优先级：`DATABASE_URL` 显式值优先（含 `${POSTGRES_PASSKEY}` 展开）；否则取 `DATABASE_URL_{env}` 并展开；否则按 `APP_ENV` 拼默认 URL；`APP_ENV` 未设时回退 `dev`。
- 启动自检：打印 `APP_ENV` 与脱敏后库名；若 `DATABASE_URL` 库名与 `APP_ENV` 不一致则拒绝启动。

### 7D.3 生产护栏（仅 prod 禁止破坏性操作）
- 禁止：`prod` 下执行 `Base.metadata.drop_all` / `scripts/import_csv --reset` / 任何清空库操作，直接报错退出；`dev`/`test` 无限制（`test` 允许 `--reset`）。（v2.4.1 起 `POST /imports` 与 `POST /data-clean-jobs/{id}/imports` **各环境均允许**——导入为幂等 upsert 非破坏性操作，原 #14 prod 拦截移除；破坏性护栏不变。）
- 仅 `prod` 需拦截，默认一律拦截；如确需重置生产，需走线下备份+受控迁移（`pg_dump hr_db_prod` 后手工操作，不经本系统 `--reset`）。
- 应用启动 `main.py` 的 `create_all` 在 `prod` 仅建缺失表，不删改已有数据。

### 7D.4 数据与运维
- 种子/导入：`testingdata/` 仅用于 `dev`/`test`，`prod` 初始数据由运维导入，操作前必须 `pg_dump hr_db_prod`。
- 三环境主数据字典独立，不自动同步。

## 9. 验收标准
1. 可通过 Org-Chart3.md 清洗 → CSV 导入全链路落库，字段、汇报关系正确；编号由系统分配（P/PA 双系列）；关闭日有值自动映射 Closed。
2. 可走通 `Planned → Open → Offered → Filled → Vacant → Closed/Frozen` 全链路，每一步有时间线事件，关闭自动写入关闭日。
3. 员工入职/离职/调岗自动联动岗位状态（Filled ↔ Vacant）。
4. 组织架构图（汇报线树）正确渲染：实线=直线、虚线=虚线；根节点并行展示；虚拟根可开关；关闭岗置灰可隐藏；跨公司连线正常。
5. 非法流转（`Planned → Filled`）与汇报成环（A→B→A）被拦截。
6. 岗位编号由系统自动生成并校验格式：正式岗 `P{seq}` / 外包岗 `PA{seq}`，纯序号；源文件编号一律忽视。
7. **主数据配置**：公司/级别/工作地点/工作范围/国家/法律强制/职位类型/税区/员工用工税额均可维护；直线/虚线经理下拉仅显示管理岗。
8. **成本字段**：三种模式（自动/手动）互斥、未启用置灰；自动模式按岗位工作地点所挂**税区**（国家或城市）正确计算公司份额与用工成本；未配置税率的地区返回「未配置」、不猜测；手动模式三个字段可填。
8a. **挂编联动**：岗位 `position_type` 与员工 `employee_type` 按映射表联动，不匹配挂载（如外包挂 Employee 编制）被拒绝。
8b. **权限隔离**：`admin` 可建号并给 `hr` 分配可管公司；`hr` **修改**未分配实体的员工/成本被拒（404/403），但岗位全局可读、组织图可显示他司员工姓名（只读）；自主注册被拒绝。
8c. **转调/升职**：转调中的人始终挂岗（原岗锁定不释放）、目标 HR 认领+分配空闲目标岗后原岗 Vacant/目标岗 Filled；升职老岗默认 Vacant（可手动 Closed）；成本/税收按财务月边界归属目标/原公司；工龄跟人（hire_date 不变）。
8d. **成本双口径**：岗位预算成本（岗位表、空岗可录、不随人、按岗位税区计算）；员工实际成本（员工表、跟人走、按人属税区计算、升职转调不丢、离职留档）；岗位详情显示预算+实际两层（Filled 对照、空岗只预算）。
9. **组织图导出**：三种 MD 格式（公司+岗位 / 直线汇报线 / 虚线汇报线）内容正确；公司聚焦视图可只看单一公司子树。
10. **导入重复校验**：CSV 内幂等键重复时报错并列出明细，不静默忽略；与库内已有幂等键匹配按更新处理（保留原编号）。
