## 1. 项目概述

### 1.1 背景
集团已有成体系的职位规则（`testingdata/原始文件/Position.md`）与组织树数据（`testingdata/原始文件/Org-Chart.md` / `Org-Chart2.md`）。数据流为：

```
原始 Org-Chart.md（或 Org-Chart2.md）
    ↓  数据清洗（系统内置模块）
Position.csv 模版文件
    ↓  用户下载、编辑、确认
上传至系统导入
    ↓  数据入库
岗位全生命周期管理 + 人员管理 + 组织架构图
```

系统覆盖三大核心能力：
1. **岗位（Position Number）全生命周期管理**：建档 → 开启 → 招聘 → 在职 → 空缺 → 关闭/冻结，全程可追溯。
2. **人员信息管理**：员工档案，并挂编到具体岗位。
3. **组织架构图 / 汇报线**：以岗位为节点生成**汇报线树**，正确展示直线（Solid-line）与虚线（Dotted-line）汇报关系。

### 1.2 目标
- Web 界面操作，**PostgreSQL** 作为持久化存储，一条命令启动。
- 数据来源为 Org-Chart 原始文件，通过清洗模块转换为标准 CSV 后导入系统。
- 岗位状态变化全程可追溯（生命周期事件时间线）。
- 组织架构图以岗位汇报关系为准，真实反映报告线。
- 外部 API 采用 JWT 认证，确保访问安全。
- 支持并发编辑，冲突时采用合理的版本控制策略。
- 开发/测试/生产三环境数据库物理隔离，同机不同库 `hr_db_{env}`，开发操作不可影响生产（见 §7D）。

### 1.3 非目标（V1 明确不做）
- 外包服务商岗位管理（`Org-Chart.md` 中的 📋 外包岗，V1 仅作参考不录入系统）。
- 多租户、复杂权限；复杂审批流；薪资、考勤、绩效、招聘全流程、社保。
- 移动端深度适配（桌面浏览器优先）。

## 2. 术语定义

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 职位 | Position | 组织最小颗粒，描述「干什么活」（职能本身），**不含工作范围**。一个职位可对应 1+ 个岗位编号。 |
| 岗位编号 | Position Number | 具体编制名额（slot），格式 `P{职位序号}-{工作范围编号}`，是生命周期管理与占用员工的主体。 |
| 工作范围 | Scope | Family(1) / Global(2) / Regional(3) / Country(4-国家编号)，决定岗位编号后缀。 |
| 隶属公司 | Company | 岗位所属法人实体（Legal Entity），如 `Peeters Capital Holding SPRL`、`Soparfi S.à r.l.`。 |
| 级别 | Level | 个人贡献者 B6~B10b / 管理岗 M7~M12b（见 §3.6）。 |
| 直线经理 | Solid-line Manager | 该岗位的直接汇报岗位，以**岗位编号**引用；唯一。构成组织树主干。 |
| 虚线经理 | Dotted-line Manager | 矩阵式职能汇报岗位（0~N 个），以**岗位编号**引用。 |
| 法律强制/可选 | Legal Mandatory / Optional | 法律强制·内部全职不可外包 / 可选（集团内控推荐）/ 纯后勤可选，三类。 |
| 职位开启日/关闭日 | Opening / Closing Date | 岗位生命周期的起止日期（数据源为年份精度）；`N/A` = 无关闭日（仍在生效）。 |
| 生命周期事件 | Position Event | 岗位每次状态变更的记录（原→新状态、时间、备注、关联员工）。 |
| 家族自然人 | Family Natural Person | 集团顶层股东（创始人/家族），非系统内岗位；P063/P066 等直报对象。 |

## 3. 岗位数据规则（源自 Position.md，系统需遵循）

### 3.1 岗位编号规则
- 格式：`P{职位序号}-{工作范围编号}`；Country 级：`P{职位序号}-4-{国家编号}`。
- 职位序号从 **P001** 起，按职位在岗位表首次出现顺序递增；同一职位多个岗位共享同一 P 序号、仅后缀不同。
- 举例：`Soparfi Managing Director` → **P063-4-5**；`Global Internal Audit Manager` → **P003-2**；`Global Film Investment Manager`（title 为 Global 但履职于美国）→ **P002-4-7**。

> ⚠️ 规则出入：现数据中 `Real Estate Compliance Manager`（P024~P027）、`Statutory MLRO Manager`（P013/P028/P054）、`Receptionist`（P045/P088）等**同一职位名使用不同 P 序号**，与「共享 P 序号」规则不符。**V1 以现有数据为准存储编号**，规则仅用于新岗位生成；新岗位生成时若遇重复职位名，沿用现有各独立序号（不强制归一）。

### 3.2 工作范围与国家/地区编号（决定后缀）
| 编号 | 工作范围 | 岗位编号后缀 |
| --- | --- | --- |
| 1 | Family（家族全域） | `-1` |
| 2 | Global（全球跨法域履职） | `-2` |
| 3 | Regional（区域） | `-3` |
| 4 | Country（国家/地区） | `-4-{国家编号}` |
| 4.1~4.9 | 比利时/丹麦/瑞典/荷兰/卢森堡/英国/美国/中国香港/中国上海 | `-4-1` … `-4-9` |

> 特别规则：2007 重组后，SPF（家族私人财富载体）归入 Family（编号 1）；Soparfi（经营性顶层控股）归入 Country·卢森堡（-4-5）。

### 3.3 工作地点（Work Location，与工作范围相互独立）
比利时布鲁塞尔 / 比利时Spa / 丹麦 / 瑞典 / 荷兰 / 卢森堡 / 英国伦敦 / 美国特拉华 / 美国纽约 / 美国洛杉矶 / 中国香港 / 中国上海。

### 3.4 汇报关系（岗位级）
- **直线经理**：直接汇报岗位（组织树上一级），岗位编号引用，唯一。
- **虚线经理**：矩阵式职能汇报。典型：各法人 MLRO 对集团 Global AML Compliance Officer（P005-2）、各投资岗对 Global Investment Governance Manager（P007-2）、各区内审联络员对 Global Internal Audit Manager（P003-2）、各区域 IT 岗对 Global System Support Specialist（P021-2）、各属地合规外包岗对 Global Contract Governance Manager（P008-2）。
- 后端校验直线关系**无环路**、虚线无重复。

### 3.5 法律强制/可选（三类，仅内部全职岗位）
| 分类 | 含义 |
| --- | --- |
| 法律强制·内部全职不可外包 | 法规必须设立、必须内部全职承担（法定高管、MLRO、资金三线、卢森堡核心决策岗等）。 |
| 可选（集团内控推荐） | 内控优化设置、推荐保留，无立法强制。 |
| 纯后勤可选 | 纯后勤性质（司机、保洁、前台等）。 |

### F1 职位与岗位生命周期管理

#### F1.1 职位（职能）维护
- 职位 = 职能名称（如 `Real Estate Compliance Manager`），一个职位可关联多个岗位编号。
- 职位列表：职位名、关联岗位数、各岗位编号与范围。

#### F1.2 岗位维护（岗位编号维度）
岗位编号为管理主体，字段对齐 Position.csv 16 列：

| 字段 | 说明 | 必填 |
| --- | --- | --- |
| 职位 | 关联职位（职能） | 是 |
| 岗位编号 | `P{序号}-{范围}`，自动生成 + 规则校验 | 是 |
| 隶属公司 | 法人实体 | 是 |
| 级别 | B/M 级别（§3.6） | 是 |
| 国家或地区 | 工作范围（Family/Global/Regional/Country·国家） | 是 |
| 职位开启日 | 生效日期（年份精度；存 date，年份→`YYYY-01-01`） | 是 |
| 职位关闭日 | `N/A`=生效中；关闭时写入 | 否 |
| 工作地点 | §3.3 列表 | 是 |
| 工作职责描述 | 1~2 句概括 | 否 |
| 直线经理 | 岗位编号引用（唯一） | 否 |
| 虚线经理 | 岗位编号引用（0~N） | 否 |
| 法律强制/可选 | §3.5 三类 | 是 |
| Org-Chart中的显示 | 组织架构图展示名 | 是 |
| **职位类型** | 职位类型（Consultant / Employee / External Employee，由 F0 主数据字典维护，岗位表单下拉选择） | **否** |
| 之前的职位 | 转岗来源岗位编号 | 否 |
| 之前的公司 | 转岗来源公司 | 否 |
| 备注 | 兼任、双线汇报、外包归集、法定任命等 | 否 |
| 税前薪资（人工） | 人工成本口径 | 否（手动模式必填） |
| 公司份额（人工） | 公司承担用工成本 | 否（手动模式可填） |
| 用工成本（人工） | 总用工成本 | 否（手动模式可填） |

- **岗位编号只能自动生成，不可手工填写**（新建时按 §3.1/§3.2 自动生成）。
- **新建岗位时以下字段可留空**：工作职责描述、税前薪资、公司份额、用工成本、备注（后续可在编辑中补充）。
- 列表：分页，按公司/工作范围/状态筛选，按名称/编号搜索。

#### F1.3 生命周期状态机（6 态，与开启/关闭日联动）
```
Planned (编制规划) ──→ Open (招聘中) ──→ Offered (已录用) ──→ Filled (在职)
     │                    │    │                                │
     ▼                    │    └──────────────┐                 ▼
  Closed/Frozen        Closed            Open             Vacant (空缺)
                       (停止招聘)       (候选人未入职)           │
                                                           ▼
                                               Closed / Frozen / Open
```
| 状态 | 说明 |
| --- | --- |
| Planned | 建档未生效；到达开启日或人工开岗 → Open |
| Open | 生效招聘中；→ Offered（录用）/ Closed（停止招聘，写入关闭日） |
| Offered | 已录用待入职；→ Filled（入职挂编）/ Open（候选人放弃） |
| Filled | 有员工占用；→ Vacant（员工离职/转岗） |
| Vacant | 曾占用现空；→ Open（重招）/ Closed（不再招聘）/ Frozen |
| Frozen | 临时冻结；→ Planned / Open（解冻） |
| Closed | 终态（写入关闭日）；如需启用建议新建岗位并记录转岗 |

- 非法流转后端拦截（如 `Planned → Filled`）。
- **导入历史数据映射**：有关闭日 → Closed（记一条关闭事件）；无关闭日 → Open（生效未占用）。

#### F1.4 生命周期历史（可追溯）
- 每次状态变更写一条事件：`岗位、原状态、新状态、变更时间、备注、关联员工`。
- 岗位详情页时间线展示；开启/关闭日写入也作为事件记录。

#### F1.5 与员工联动
| 员工动作 | 岗位联动 |
| --- | --- |
| 入职挂编 | 岗位 → **Filled**，绑定员工 |
| 离职 / 转岗出岗 | 岗位 → **Vacant**，解绑员工，生成事件 |
| 岗位间调岗 | 旧岗 → Vacant；新岗 → Filled |

- **挂编条件**：仅岗位状态为 **Open / Vacant / Offered** 时可挂编；**Filled**（已被占用）、**Closed / Planned** 时拒绝挂编。
- **调岗约束**：新岗位同样须为 Open / Vacant；旧岗随调出转 Vacant。

#### F1.6 岗位成本字段与公司份额计算
- 岗位有三个**人工成本**字段：**税前薪资（人工）**、**公司份额（人工）**、**用工成本（人工）**。
- 两种输入模式，**互斥，只能启用一种**；未启用的字段置灰不可编辑：
  1. **自动计算模式**：公司份额 = 税前薪资 × Σ(该岗位国家全部税务科目税率)；用工成本 = 税前薪资 + 公司份额。
  2. **手动输入模式**：三个字段均可手工填写。
- **员工用工税额配置**（F0 主数据）：
  - 按**国家**划分，每个国家有各自特定的税务项目。
  - 用户可直接增加项目，每项含：**科目**（如 Social Security、Pension、Insurance）与**税率**（百分比）。
  - 自动计算时按岗位所属国家的全部有效科目税率求和。

### F2 人员信息管理

#### F2.1 员工列表
分页，按公司/部门、员工类型、在职状态筛选，按姓名/工号搜索。

#### F2.2 员工字段
| 字段 | 说明 | 必填 |
| --- | --- | --- |
| 工号 | 唯一 | 是 |
| 姓名 | — | 是 |
| 性别 | 男/女/其他 | 是 |
| 出生日期 | — | 否 |
| 手机 / 邮箱 | 联系方式 | 否 |
| 入职日期 | — | 否 |
| 员工类型 | 正式/实习/外包/劳务 | 是 |

- **员工必须挂岗（V1 不允许「待分配」）**：新建员工必须指定岗位编号；岗位随即转 **Filled**（见 F1.5）。岗位已被占用 / 关闭 / 编制中时禁止挂编。
- **新建员工时以下字段可留空**：出生日期、手机、邮箱、备注。
- **汇报关系由岗位继承**：员工挂编后，其直线/虚线经理 = 所挂岗位的直线/虚线经理岗位（的员工），不在员工层单独维护（V1）。
- 员工详情页：档案 + 当前岗位 + 汇报关系 + 入职/离职/调岗入口。

### F3 组织架构图 / 汇报线（岗位级，汇报线树）

#### F3.1 视图形态（主视图 = 汇报线树）
- **节点 = 岗位编号**，卡片显示：Org-Chart中的显示名、岗位编号、隶属公司、占用状态（Filled 显示在职员工姓名）。**不显示职级**。
- 按 **Position.csv 直线经理** 关系构建层级树。
- **根节点** = 直线经理为 `N/A` 的岗位：`P063-4-5 Soparfi Managing Director`、`P066-1 SPF Asset Compliance Manager`（含已关闭的 `P001-1`）。多个根并行展示。
- **虚拟根节点（默认开启）**：「家族自然人股东」作为图顶虚拟根节点，将 P063/P066（及其下全部子树）归拢；提供开关可关闭，关闭后恢复多根并行展示。
- 跨公司汇报正常连线（如 P051 → P004-1、P033 → P082），不以公司为容器。

#### F3.2 直线 / 虚线展示
- 直线汇报：**实线**连接（父→子）。
- 虚线汇报：**虚线 / 不同颜色**连接，悬浮标注「虚线汇报」。
- 后端校验直线无环路、虚线无重复。

#### F3.3 交互
- 节点展开/折叠；**缩放/平移需真正可用、手感良好**（滚轮缩放、拖拽平移、适应窗口按钮）。
- **布局可读性**：层级清晰、避免全部节点横向挤成一排；长文本自动截断，悬浮显示完整信息。
- **公司聚焦视图**：选中一个公司 → **只看该公司及其岗位的子树**（聚焦展开，非仅高亮），一键返回全局视图。
- 按工作范围 / 状态筛选；悬浮显示摘要（职位、岗位编号、公司、级别、占用员工、汇报关系）；点击跳转岗位详情。
- 已关闭（Closed）岗位置灰展示，可切换「含已关闭岗位」。
- 孤立/成环异常岗位在底部单独列表提示（导入期校验兜底）。

#### F3.4 辅助视图（轻量）
- 岗位列表/表格视图：按公司、工作范围、状态分列展示占用情况（Filled / Vacant / Open 等）。公司分组的组织树视图列为 V1.1 扩展。

#### F3.5 导出 MD（类似 Org-Chart.md 组织架构）
组织架构图支持导出 Markdown，**3 种格式**：
1. **Org-chart 格式**：公司 + 岗位层级（**不含汇报线**），按公司分组展示岗位。
2. **直线汇报线格式**：按直线经理关系输出层级树（含汇报线）。
3. **虚线汇报线格式**：输出虚线汇报关系（各岗位的虚线经理）。

- 导出内容沿用节点卡片信息（岗位编号、显示名、公司、级别、状态）。
- 前端生成 `.md` 文本下载；后端提供等价导出接口（可选）。

### F4 数据导入（Position.csv）
- V1 支持导入 `Position.csv`（16 列 91 行）作为初始数据，含全部 16 字段。
- 校验规则：
  - 岗位编号唯一且格式合法（`P{序号}-{范围}`，Country 级必须 `-4-{编号}`）。
  - **CSV 文件内岗位编号重复 → 报错**（返回错误明细，该行不导入），不再静默忽略/覆盖。
  - 直线/虚线经理引用必须存在；`N/A` 视为空。
  - 关闭日早于开启日报错；开启/关闭日按年份精度解析。
  - 导入幂等：与库内已有岗位编号重复按编号更新字段（保留事件与员工关联），重复导入不产生重复数据。
- 导入后自动生成初始生命周期事件（Closed 岗记录关闭事件）。

### F5 Org-Chart 数据清洗（上传解析 → CSV 生成）

上传 Org-Chart.md，按 Position.csv 模版格式自动解析、清洗，输出标准 CSV 后一键导入系统。

1. 用户上传 Org-Chart.md（规则文件 Position.md 使用固定模版）
2. 系统解析树形结构，提取所有 🧑‍💼 内部全职岗位（排除外包岗 📋）

4. 用户在前端预览清洗报告 + CSV 数据
5. 确认后一键导入系统（复用 F4 幂等 upsert）

#### F5.2 解析能力

  - 格式 A：` ```tree ` 代码块（如 Org-Chart.md）

- 仅提取内部全职岗位（🧑‍💼 In-house + 👨‍👩‍👧 Family Volunteer），排除外包岗 📋

#### F5.3 8 个关键字段读取规则
| 字段 | 读取方式 |
| --- | --- |

| 法律强制/可选 | 从树节点的 `【...】` 注解提取 |

## 7B. 安全需求（JWT 认证）

### 7B.1 外部 API 认证
- 外部调用的 API 端点（如 `/api/public/*` 以及非内部工具消费的接口）必须通过 **JWT（JSON Web Token）** 认证。
- 内部管理接口（系统前端使用）采用基于会话/Token 的简单认证（V2 阶段考虑完整用户管理）。
- JWT Token 包含：用户标识、角色、过期时间。
- Token 过期后需刷新；无 Token 或过期 Token 返回 `401 Unauthorized`。
- 请求头格式：`Authorization: Bearer <token>`。

### 7B.2 安全措施
- 密码（如有用户系统）使用 bcrypt 哈希存储。
- API 请求速率限制（防止滥用）。
- 输入校验：所有接口输入均经过 Pydantic 校验，防止注入。
- PostgreSQL 连接使用参数化查询（SQLAlchemy ORM 天然支持），防 SQL 注入。

## 7C. 并发控制（乐观锁）

### 7C.1 冲突场景
系统为多人可同时使用的 Web 应用，需处理：两人同时编辑同一条岗位/员工数据。

### 7C.2 策略：乐观锁（版本号控制）
- 核心数据表（`position_numbers`、`employees`）增加 `version` 字段（整数，每次更新递增）。
- **读取**时返回当前版本号。
- **更新**时必须携带客户端持有的版本号：`UPDATE ... WHERE id = ? AND version = ?`。
- 若影响行数为 0（版本已变更），返回 `409 Conflict`，提示客户端刷新数据后重试。
- 前端在保存时携带版本号；收到 409 时提示用户「数据已被他人修改，请刷新后重试」。

### 7C.3 不需要锁的场景
- 岗位状态流转（POST /positions/{id}/events）：状态机本身有合法转换白名单，天然幂等/可重入，无需版本校验。
- 员工入职/离职：由状态机保证一致性。

## 7D. 多环境与数据库隔离（dev / test / prod）

### 7D.1 环境与命名
- 三环境取值固定：`APP_ENV=dev|test|prod`（默认 `dev`），大小写不敏感。
- 同机不同库，库名强制 `hr_db_{env}`：`hr_db_dev` / `hr_db_test` / `hr_db_prod`，禁止自定义库名/复用同一库。
- 同一 PostgreSQL 实例内三库并存，账号可共用但生产建议独立最小权限账号。

### 7D.2 配置与文件约定
- 环境变量：`APP_ENV`（环境）+ `DATABASE_URL`（连接串，库名必须与 `APP_ENV` 一致）。
- 文件约定（均 gitignored，示例见 `.env.example`）：
  - `.env`       → dev   `DATABASE_URL=postgresql://user:password@localhost:5432/hr_db_dev`
  - `.env.test`  → test  `DATABASE_URL=postgresql://user:password@localhost:5432/hr_db_test`
  - `.env.prod`  → prod  `DATABASE_URL=postgresql://user:password@localhost:5432/hr_db_prod`
- 加载优先级：`DATABASE_URL` 显式值优先；否则按 `APP_ENV` 拼默认 URL；`APP_ENV` 未设时回退 `dev`。
- 启动自检：打印 `APP_ENV` 与脱敏后库名；若 `DATABASE_URL` 库名与 `APP_ENV` 不一致则拒绝启动。

### 7D.3 生产护栏（仅 prod 禁止破坏性操作）
- 禁止：`prod` 下执行 `Base.metadata.drop_all` / `scripts/import_csv --reset` / 任何清空库操作，直接报错退出；`dev`/`test` 无限制（`test` 允许 `--reset`）。
- 仅 `prod` 需拦截，默认一律拦截；如确需重置生产，需走线下备份+受控迁移（`pg_dump hr_db_prod` 后手工操作，不经本系统 `--reset`）。
- 应用启动 `main.py` 的 `create_all` 在 `prod` 仅建缺失表，不删改已有数据。

### 7D.4 数据与运维
- 种子/导入：`testingdata/` 仅用于 `dev`/`test`，`prod` 初始数据由运维导入，操作前必须 `pg_dump hr_db_prod`。
- 三环境主数据字典独立，不自动同步。

13. **三环境隔离**：`dev` 执行 `--reset` 仅清空 `hr_db_dev`，`hr_db_prod` 不受影响；`prod` 下 `--reset`/`drop_all` 被拦截报错；`.env` / `.env.test` / `.env.prod` 示例可一键切换（见 7D）。

## 10. 已确认决策与开放问题

### 已确认决策（2026-08-03）
- **数据权威**：以 `Position.csv` 为准（§3.7）。
- **组织图主视图**：汇报线树（§4 F3）。
- **外包岗位**：V1 仅内部全职，外包岗不入系统（§1.3）。
- **虚拟根节点**：「家族自然人股东」虚拟根**默认开启**，可开关（§4 F3.1）。
- **员工必须挂岗**：V1 不允许「待分配」员工，`当前岗位` 必填；挂编须岗位为 Open / Vacant（§4 F2.2 / F1.5）。
- **年份精度**：开启/关闭日数据源为年份，系统存 date，年份→`YYYY-01-01`（§4 F1.2）。
- **虚线汇报**：现数据以单虚线为主，模型按 0~N 设计（junction 表），V1 使用统一虚线编辑入口，不单独做多虚线管理模块（§4 F3.2）。
